# Context-rot benchmark: method and reporting contract

## Question
On the same synthetic repository and task, does actual Leadline context change an agent's tendency to choose a planted stale answer? This is a small local evaluation, not a claim of general reliability or a test against production.

## Paired design
- Materialize fresh directories from versioned synthetic fixtures. Each case has plausible overlapping context and an authoritative observable source. Grading keys are outside the agent-visible directory.
- Use independent agent contexts per arm. Both arms receive the same question, source access, model, limits and output schema. Only the on arm gets the actual product's context/integration. Off must not receive product hints or the answer key.
- Record case/pair/arm, fixture and product identities, model/harness, prompt, raw response, execution status and elapsed time. A repository name or example identifier is not a secret; no personal transcripts or credentials belong in this evaluation.
- Alternate arm order by case. Do not feed off results into on prompts. Declare repeated trials and all exclusions; preserve the first batch even when later fixes improve results.
- Score structured final decisions against a frozen exact key. Distinguish correct, planted-stale, other incorrect, abstention and invalid/failed. Cite-evidence accuracy and task success are separate from stale-answer rate.

## What the numbers mean
Report counts and denominators for each arm, paired transitions and unpaired/failed trials. Zero observed stale answers in a tiny sample is not proof of prevention. A stale-answer reduction accompanied by universal abstention is not an effective solution: show correctness and abstention beside it. Multiple trials from one scenario are not independent scenario diversity.

A deterministic fixture test that a hook emits a warning is **not an agent trial**. A scripted adapter that selects the expected answer is useful for harness tests only. Reading an on-arm hand-crafted correct summary does not evaluate Leadline; on input must be generated by the reviewed executable, and its source identity retained. MCP-only trials measure assistance, not mandatory host enforcement.

## Scope and controls
Include stale deployment/config pointers, an already-existing daemon, superseded API/endpoint, stale claim inside a fresh file, ledger reversal, partial-evidence/positive-control failures, stale handoff, provenance mismatch and ignored-warning cases. Include unchanged-old and unknown-freshness controls to expose false alarms. Provenance mismatch by itself must not make a correct answer wrong.
